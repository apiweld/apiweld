This is the shortest path that produces a real client. The example selects two Stripe refund operations. Swap in any API the catalog knows.

You need Node.js 20 or newer. Apiweld is one package: the CLI and the MCP server are the same program.

<PackageManagers pkg="apiweld" dev />

<Aside type="note" title="What this does not set up">
  There is no account to create and no project to provision in a cloud console. `apiweld init` writes files in the repo you are already in.
</Aside>

## Initialize

<Steps>
  <Step title="Create the config">

`apiweld init` writes `apiweld.config.ts` and adds `.apiweld/` to `.gitignore`. Pass `--agents` to append a short section to `AGENTS.md` or `CLAUDE.md` and to print the MCP config snippet for common agents.

In a workspace — a `package.json` `workspaces` field, or `pnpm-workspace.yaml` — `init` lists the packages and asks where generated clients should go. Press Enter to keep `src/apis`, or pass `--output` to skip the prompt. The path is relative to the directory you run `init` in. Outside a workspace, `init` writes `output: "src/apis"` without asking.

`bun run` and `npm run` execute scripts from the package root, so a script started in a package still writes the config there. Point `--cwd` at the package when the config should live next to that app:

```sh
npx apiweld init --agents
npx apiweld init --output packages/web/src/apis
```

The agent note tells the model to reach for Apiweld instead of hand-writing `fetch` or installing a full vendor SDK.

  </Step>
  <Step title="Add the provider">

Index one spec when you need it. `catalog add` fetches that OpenAPI document, stores it in the local catalog, and leaves every other provider alone. A GitHub `blob` URL is fetched as the raw file.

```sh
npx apiweld catalog add stripe https://github.com/stripe/openapi/blob/master/latest/openapi.spec3.json
```

`catalog sync` still downloads the prebuilt snapshot from a GitHub release and checks its SHA-256. `catalog build` indexes APIs.guru on this machine. That full build is the slow path. Agents should add the providers a repo actually calls.

  </Step>
  <Step title="Find the operation">

Search hits API titles and operation summaries. `--ops` searches endpoints. `show` prints a compact TypeScript-shaped signature instead of a raw OpenAPI blob. Pass an operation id or `METHOD /path`.

```sh
npx apiweld search "refund a payment" --ops
npx apiweld show stripe PostRefunds
```

  </Step>
  <Step title="Weld the client">

`add` records the operations, generates the client, and updates the lock. An operation id and its `METHOD /path` select the same call. The config and the lockfile store `METHOD /path`. The config key is the name you will import. If that provider is already in the catalog, you can omit `--source`.

```sh
npx apiweld add stripe PostRefunds GetRefundsRefund
npx apiweld add stripe "POST /v1/refunds" "GET /v1/refunds/{refund}"
```

You should now have a client under the configured `output` directory (default `src/apis/stripe/`), a lock entry, and a config block you can read in review. Commit all three. Generated code is part of the project.

  </Step>
</Steps>

## What the agent does instead

Register the server once (`apiweld mcp`, stdio, no port). The agent then calls `search_operations`, `describe_operation`, and `add_operations`. Those tools map one-to-one onto the commands above. The tool result includes the import path and an example call, so the agent can wire the client without rereading the spec.

## Generate again without the network

`apiweld generate` rebuilds from the lock and the content-addressed spec cache. Use it in CI when you want to prove the committed client still matches the lock.

```sh
npx apiweld generate
npx apiweld verify
```

`verify` runs the TypeScript compiler against the project's `tsconfig.json`, then an optional test command if you configured one.
